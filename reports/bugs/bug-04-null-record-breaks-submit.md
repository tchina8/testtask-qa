# BUG-04 — повреждённая запись в хранилище выводит форму из строя: «Отправить» не делает ничего

- **Серьёзность:** критичный
- **Где:** `http://localhost:8765/`, форма регистрации целиком — обработчик
  `submit`, проверка занятости email (`app/index.html`, строка 308:
  `String(items[i].email)`)
- **Ширина экрана:** 1280 (от ширины не зависит — дефект в логике, не в вёрстке)
- **Найден:** аудит (сессия 3), находка А-01. Значения вне перечня шаблона:
  ни тест-план, ни исследовательское тестирование, ни наивный прогон эту область
  не закрыли — все три смотрели на приложение снаружи, а второе незащищённое
  обращение к элементу массива видно только в коде.

## Шаги воспроизведения

1. Поднять стенд: `npx --yes http-server ./app -p 8765 -c-1`, открыть
   `http://localhost:8765/`.
2. В консоли браузера записать в хранилище массив с испорченным элементом:
   ```js
   localStorage.setItem('registrations', '[null]');
   ```
3. Перезагрузить страницу.
4. Заполнить форму **корректными** данными: Имя `Аудит`, Email
   `audit@mail.ru`, Пароль `Parol123`, Повтор `Parol123`, согласие отмечено.
   Email обязан быть корректным по формату — на этом шаге дефект и держится
   (см. «Границы находки»).
5. Нажать «Отправить».
6. Посмотреть на страницу и в консоль браузера.

## Ожидаемый результат

Регистрация проходит: появляется подтверждение, запись добавляется в список,
поля очищаются.

`SPEC.md` → «Сценарии», п. 1 (основной): «Пользователь заполняет все пять полей
корректно и нажимает „Отправить“ → появляется подтверждение, запись добавляется
в список зарегистрированных, поля очищаются».

Если по какой-то причине регистрация не проходит, пользователь обязан увидеть
ошибку: `SPEC.md` → «Состояния» — в таблице ровно четыре строки, и состояния
«нажал кнопку, не произошло ничего» среди них нет. Строка **«Ошибка»**
предполагает «Сообщения у конкретных полей».

Содержимое `localStorage` при этом задано (`SPEC.md` → «Поля и правила»:
ключ `registrations`, значение — JSON-массив), а поведение при **испорченном**
содержимом — нет. Дефект не в том, что приложение не чинит чужие данные,
а в том, что оно из-за них перестаёт выполнять свою основную функцию
и не сообщает об этом ни словом.

## Фактический результат

Обработчик `submit` падает с необработанным исключением **до конца валидации**,
на проверке занятости email. Пользователь нажимает «Отправить» и не получает
ничего: ни сообщений об ошибках, ни подтверждения, ни записи в списке. Кнопка
выглядит рабочей и не реагирует.

```
Uncaught TypeError: Cannot read properties of null (reading 'email')
```

Состояние из интерфейса не лечится: очистить или починить хранилище со страницы
нельзя, а каждая следующая попытка отправки падает так же. Для пользователя,
не открывающего консоль, приложение просто сломано.

Причина — второе незащищённое обращение к элементу массива, помимо того, что
описано в [BUG-03](bug-03-broken-storage-blank-list.md):

- `app/index.html:268` — `item.name` в `render()`. Это BUG-03: падает отрисовка
  списка, последствие косметическое (пустое место под заголовком).
- `app/index.html:308` — `String(items[i].email)` в цикле проверки дубликата.
  Это BUG-04: падает отправка формы, последствие — потеря основной функции.

**Отношение к BUG-03.** Тот же корень (`null` внутри массива записей), разные
последствия и разная серьёзность. BUG-03 оформлен как «низкий» с формулировкой
«дефект настоящий, но редкий», и в `reports/test-run.md` состояние приложения
описано словами «Форма при этом работает во всех пяти случаях». Проба, на
которую опирается это утверждение (`tests/probe-s02-s04-s08.mjs`, раздел S-04),
меряет поле `formVisible` — видна ли форма, — и ни в одном из пяти случаев
повреждения не нажимает «Отправить». Поэтому дефект и не был замечен.
BUG-03 остаётся в силе как есть: он про отрисовку, этот — про отправку.

## Доказательство

**Что выполнено фактически.** Стенд `http://localhost:8765/` в сессии, где
находка сделана, поднять не удалось: Node в окружении отсутствует
(`C:\Program Files\nodejs\node.exe` → `False`, `node_modules/` нет,
`npx` не найден). Доказательство снято встроенным браузером сессии, который
отдаёт файл как `data:`-URL, где настоящий `localStorage` заблокирован
(`Storage is disabled inside 'data:' URLs`); поэтому `localStorage` подменён
in-memory заглушкой, а обработчик вызван через
`form.dispatchEvent(new Event('submit', { bubbles: true, cancelable: true }))`.

Подмена результат не искажает: падение происходит в сравнении строк внутри
цикла, и единственное, что делает код с хранилищем до этого места, — `getItem`,
который заглушка возвращает дословно.

Хранилище `[null]`, поля заполнены валидными данными:

```
{
  "исключение": "Uncaught TypeError: Cannot read properties of null (reading 'email')",
  "видимые_ошибки": [],
  "подтверждение_видно": false,
  "записей_в_хранилище": "[null]",
  "записей_в_списке": 0,
  "поля_после_отправки": ["name=\"Аудит\"", "email=\"audit@mail.ru\"",
                          "password=\"Parol123\"", "confirm=\"Parol123\"", "agree=true"]
}
```

Читается так: исключение есть, ошибок на экране ноль, подтверждения нет, запись
не создана, введённые данные остались в полях. Ни одного признака того, что
нажатие вообще обработано.

Контрольные пробы — они же граница находки:

```
[null] + невалидный email        → исключения нет, показана ошибка
                                   "Введите корректный email"
[{"name":"Без почты"}] + валидный email
                                 → исключения нет, регистрация проходит
[null] повторно                  → то же исключение, воспроизводится стабильно
```

**Как воспроизвести на нормальном стенде** (проверка, которую я выполнить
не смог). Поднять стенд, пройти шаги 1–6 выше и снять два факта: содержимое
консоли браузера и состояние страницы. Ожидается `Uncaught TypeError: Cannot
read properties of null (reading 'email')` в консоли и полное отсутствие
изменений на странице. Одной строкой для проверки состояния после клика:

```js
JSON.stringify({
  ошибки: [...document.querySelectorAll('.error')]
    .filter(e => e.offsetParent !== null && e.textContent.trim()).map(e => e.textContent.trim()),
  подтверждение: document.getElementById('notice').offsetParent !== null,
  записей: document.querySelectorAll('li').length
})
```

**Почему скриншот здесь бесполезен.** Картинка покажет заполненную форму без
единого сообщения — ровно то же, что видно за мгновение до любого нормального
нажатия. Отличить «кнопка не нажата» от «нажата и упала» можно только по
исключению в консоли и по тому, что запись не появилась. Поэтому доказательство
здесь — вывод консоли; скриншот не прикладывается.

## Границы находки

Дефект требует двух условий одновременно: в `localStorage` лежит массив
с элементом `null` **и** введённый email проходит проверку формата. При
невалидном формате выполнение до цикла дубликата не доходит, и форма отвечает
нормально — то есть пользователь с испорченным хранилищем увидит осмысленную
ошибку на неправильном адресе и мёртвую кнопку на правильном. Запись без поля
`email` (`[{"name":"Без почты"}]`) не падает: `String(undefined)` допустим.

Испорченное содержимое в обычной работе приложение себе не создаёт. Реальные
пути те же, что у BUG-03: ручная правка через инструменты разработчика,
коллизия с другим приложением на том же домене, оборванная запись при закрытии
вкладки.

**Почему всё-таки «критичный», а не «низкий», как у BUG-03, и не «блокер».**
Не блокер: на чистом стенде основной сценарий проходит, состояние достижимо
только при повреждении хранилища извне. Не низкий: попав в это состояние,
пользователь теряет саму возможность зарегистрироваться, без сообщения
и без способа выйти из состояния средствами страницы. Редкость входа
компенсируется полнотой отказа на выходе.
