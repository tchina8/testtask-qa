# Задание 4 (QA): проверка формы регистрации, написанной агентом

Продукт этой работы — **тестовая работа**, а не форма. Форму написал агент
в отдельной сессии по короткому промпту-заказу; дальше она тестировалась как чужое
приложение: код не читался и не правился.

Что здесь есть: тест-план на 12 проверок, отчёт о прогоне, четыре баг-репорта,
падающий автотест, 19 артефактов-доказательств, сравнение двух прогонов,
независимый аудит и журнал работы по сессиям.

**Прежде чем читать отчёты, прочитайте [«Аудит и его находки»](#аудит-и-его-находки).**
Аудит проведён в отдельной сессии с чистым контекстом и нашёл в этой работе
пятнадцать проблем, включая одну критичную ошибку в самом отчёте о прогоне.
Две находки закрыты, тринадцать оставлены как есть — с явным решением
и без правки задним числом.

Требования, с которыми всё сверяется, — в [SPEC.md](SPEC.md).
Правила работы — в [AGENTS.md](AGENTS.md).

## Запуск

Все команды выполняются **из корня проекта**. Оболочка — PowerShell, Windows.

**Шаг 0. Обновление PATH — обязательно первым в каждой новой оболочке.**
Node установлен уже после старта окружения, поэтому в оболочках сессии `node`
по умолчанию не виден и падает с `CommandNotFoundException`. Это **не** значит,
что Node отсутствует.

```bash
$env:Path = [System.Environment]::GetEnvironmentVariable("Path","Machine") + ";" + [System.Environment]::GetEnvironmentVariable("Path","User")
```

**Шаг 1. Зависимости** (один раз):

```bash
npm install -D @playwright/test
```

```bash
npx playwright install chromium
```

**Шаг 2. Стенд.** Отдельная оболочка, оставить работающей:

```bash
npx --yes http-server ./app -p 8765 -c-1
```

Адрес — строго `http://localhost:8765/`. Сервер поднимается из папки `app`,
поэтому форма открывается по корню, без `/app/` в пути. Флаг `-c-1` отключает
кеш: без него после фикса бага страница отдаётся из кеша, и повторная проверка
покажет старое поведение. Если 8765 занят — остановиться и спросить,
а не брать соседний порт.

**Шаг 3. Автотест.** При поднятом стенде:

```bash
npx playwright test --reporter=list
```

**Фикс BUG-01 применён и закоммичен** (`49dad6b`), поэтому на текущем состоянии
репозитория тест зелёный. Сохранены оба вывода:

- **до фикса — 2 failed.** Тест падал намеренно, на реальном дефекте:
  страница шире окна на 4047 px при 1280 и на 4583 px при 360.
  Вывод: [reports/playwright-run.txt](reports/playwright-run.txt).
- **после фикса — 2 passed.** Вывод: [reports/playwright-retest.txt](reports/playwright-retest.txt).

Правку делала отдельная сессия-фиксер; тестировщик её не писал и не читал —
об объёме судил по наблюдаемому поведению. Что именно проверено после фикса
и что осталось сломанным — [reports/retest.md](reports/retest.md).

### Вспомогательные скрипты

Не автотесты: проверок внутри нет, они печатают факты и снимают доказательства.
Автотест в проекте ровно один — `tests/bug-01-overflow.spec.js`.

```bash
node tests/capture-evidence.mjs
```
Снимает 12 скриншотов в `reports/screenshots/` на ширинах 360 и 1280.

```bash
node tests/probe-s02-s04-s08.mjs
```
Исследовательские пробы: двойная отправка, повреждённое хранилище, две вкладки.

```bash
node tests/probe-naive-claims.mjs
```
Перепроверка утверждений наивного прогона на настоящем стенде.

## Что не сделано

**BUG-02, BUG-03 и BUG-04 не чинились** — фикс делался по одному баг-репорту.
Оба воспроизводятся после фикса без изменений, это зафиксировано в отчёте
о повторной проверке.

**Сценарий S-09 (значение вставлено из буфера) не проверен.**
Не по нехватке времени, а по выбору способа: первый полный сценарий выполнен
настоящим набором с клавиатуры, остальные проверки заполняли поля скриптом —
через нативный сеттер `value` с событиями `input` и `change`. Такой ввод
**по построению** не может поймать дефект «форма не видит вставленное значение»:
скрипт сам генерирует те события, которых при реальной вставке может не быть.
Плата за скорость названа задним числом, а не в момент выбора — разбор
в [reports/discrepancies.md](reports/discrepancies.md), раздел 2.

**BUG-05 и BUG-06 не заведены.** Два дефекта найдены наивным прогоном
и подтверждены мной на стенде 8765: сбой записи в `localStorage` проглатывается
молча (пользователь не видит ни успеха, ни ошибки), и битые данные затираются,
а запись без `email` рисуется как буквальное `undefined`. Баг-репорты не оформлены,
потому что находки чужие, а решение — за владельцем требований. Доказательства
сняты: [reports/probe-naive-claims.txt](reports/probe-naive-claims.txt).
(До аудита эти два места резервировались под номерами BUG-04 и BUG-05. Номер 04
занял реально оформленный баг-репорт по находке аудита; резерв — не выданный
номер, а перенумеровывать заведённое правила запрещают, поэтому сдвинулся
именно резерв.)

**Сессия-автор приложения журнала не оставила** (коммит `bc4d1f9`, файла сессии
нет). Поэтому расхождений вида «агент-автор отчитался „готово“ — проверка
опровергла» собрать не из чего; вместо них в списке расхождений четыре случая,
где ошибался тестировщик. Это оговорено в шапке файла, а не подогнано
под формулировку критерия.

## Аудит и его находки

Результат прогнан через независимый взгляд: **отдельная сессия, роль «Аудитор»,
чистый контекст** — тот, кто проверял, работу не делал и подсказок о ней
не получал. Задача была прямая: найти пункты `SPEC.md` без покрытия, места, где
отчёт говорит «пройдено» без доказательства, дефекты приложения, которые прогон
не поймал, и формулировки плана, которые ничего не различают. Полный текст —
[reports/audit.md](reports/audit.md).

**Найдено 15 проблем: 2 критично, 5 важно, 8 мелочь.** Ниже — что с ними стало.

### Закрыто

**А-01 — дефект приложения, который прогон не поймал, и прямая ошибка в отчёте.**
Незащищённое обращение к элементу массива есть не в одном месте, а в двух:
`app/index.html:268` (отрисовка — это BUG-03) и `app/index.html:308` (проверка
дубликата внутри отправки формы). При `registrations = [null]` в хранилище любая
отправка с корректным по формату email падает с `TypeError` до конца валидации:
пользователь не получает ни ошибки, ни подтверждения, ни записи. При этом
[reports/test-run.md](reports/test-run.md) утверждает «Форма при этом работает
во всех пяти случаях» — утверждение опровергнуто. Прогон этого не увидел,
потому что проба меряла `formVisible` (видна ли форма), а кнопку не нажимала
ни разу. **Заведён [BUG-04](reports/bugs/bug-04-null-record-breaks-submit.md),
серьёзность критичная.**

**А-02 — ограничение доказательной базы, см. следующий раздел.**

### Принято к сведению, оставлено как есть

Тринадцать находок (В-01…В-05, М-01…М-08) **осознанно оставлены без правок —
не хватило времени до сдачи**. Это решение владельца требований, а не
недосмотр. Чтобы его можно было проверить, вот что при таком решении остаётся
в репозитории неточным:

- **В-01.** В BUG-03 строка таблицы «обрыв JSON → `pageerror`» подкреплена
  чужой ошибкой: в `tests/probe-s02-s04-s08.mjs` слушатель вешается до первого
  `goto`, хранилище между итерациями не чистится, и след от предыдущего случая
  (`[null]`) уехал в отчёт. Сам BUG-03 доказан другой строкой и остаётся в силе.
- **В-02.** Вывод ретеста «16 из 16 в ожидаемом состоянии» получен чек-листом,
  который в TC-01, TC-02, TC-07 и TC-08 проверяет меньше, чем требует план —
  в частности, не проверяет сохранность введённых данных после неудачной
  отправки.
- **В-03.** Сценарий S-03 сам объявил дефектом отказ на адресе, который
  принимает браузер; прогон нашёл ровно это (`a@b`) и записал «без дефектов».
  План и отчёт противоречат друг другу; `a@b.c` того же класса не проверял никто.
- **В-04.** Состояние «Есть данные» из `SPEC.md` не является ожидаемым
  результатом ни одной проверки плана; возврат после перезагрузки проверен
  на одной записи, не на нескольких.
- **В-05.** Четыре ожидаемых результата ничего не различают — в том числе
  «форма в состоянии „не отправлено“» (наблюдаемого признака у формы нет вообще)
  и «появляется подтверждение» без слова «видимое», на чём прогон споткнулся
  трижды подряд.
- **М-01…М-08.** Мелочи: чекбокс не получает отметки ошибки; скриншоты 360
  приписаны проверкам, объявленным на 1280; ретест не ответил на один пункт
  собственного списка; неверная арифметика во входе S-10; расхождение
  «`SPEC.md` говорит, что пароль в хранилище, — его там нет»; фраза «обрезка
  согласована во всех трёх точках» не учитывает, что пароль не тримится;
  три подтверждённых расхождения без баг-репортов; артефакты сняты в другом
  окружении.

Ни одна находка не удалена и не смягчена: `reports/audit.md` лежит в репозитории
целиком, вместе с разделом о том, что аудит подтверждает.

**Отчёты задним числом не переписывались.** `reports/test-run.md` сохраняет
опровергнутую строку про работающую форму, BUG-03 — свою серьёзность и свою
недоказанную строку. Правило проекта — журнал и отчёты только дополняются;
исправление вместо новой записи прячет ошибку вместо того, чтобы её показать.
Поэтому опровержение живёт рядом, в BUG-04 и в аудите, со ссылками в обе стороны.

Что нужно, чтобы закрыть: переснять вывод по проверкам плана на поднятом стенде
и положить его в `reports/`. Не сделано — не хватило времени до сдачи.

## Упрощения и границы

**Приняты сознательно, до начала работы** (`SPEC.md` → «Чего точно не делаем»):

- Нагрузочного и кроссбраузерного тестирования нет.
- Аудита доступности по WCAG нет. Наивный прогон нашёл в этой области настоящие
  проблемы (нет `aria-invalid`, фокус не переводится на первое невалидное поле,
  чекбокс 13×13 px) — они за границей объёма, но не выдуманы.
- Тестирования безопасности нет. Пароль в `localStorage` открытым текстом —
  осознанное допущение учебного стенда, баг-репорты на эту тему не заводятся.
  (Фактически приложение пароль вообще не сохраняет — проверено в TC-03.)
- Автоматизирован ровно один сценарий. Остальные 11 проверок плана — ручные,
  с доказательством на каждую.

**Возникли по ходу:**

- **Скриншоты снимает Playwright, а не встроенный браузер сессии.** У встроенного
  браузера `screenshot` падает с `the Browser pane is not displayed`, а к концу
  сессии перестали доходить и синтетические клики: событие `submit` не приходило
  вовсе, при том что программный `btn.click()` работал. Всё, что зависит
  от настоящей мыши или картинки, ушло в Playwright.
- **Три недосказанности `SPEC.md`** (пробелы по краям, регистр email в дубликате,
  максимальная длина полей) отработаны как **наблюдения**, а не как проверки
  с ожидаемым результатом: ожидаемое поведение там не задано. Все три оказались
  внутренне непротиворечивыми, поэтому дефектов из них не вышло — разбор
  в отчёте о прогоне.
- **Линтера и форматтера в проекте нет намеренно:** приложение — один файл,
  тулинг не окупается.
